# Revocable Megakernels: Cooperative GPU Scheduling for Predictable LLM Serving

## Overview

Modern Large Language Model (LLM) inference systems use GPU megakernels to improve execution efficiency by fusing multiple operations into persistent GPU kernels. These megakernels execute graphs of tiled tasks using an in-kernel scheduler, reducing kernel-launch overhead and improving inference performance.

However, efficient execution does not necessarily guarantee responsiveness when multiple workloads with different priorities share a GPU. Once a megakernel is executing, an urgent request may have to wait for the ongoing background workload to finish. CUDA stream priorities cannot interrupt kernels that are already executing.

This project investigates **Revocable Megakernels**, a cooperative GPU scheduling mechanism that allows an executing megakernel to safely yield GPU resources to urgent workloads and resume execution afterward.

## Motivation

Traditional GPU kernel execution provides limited opportunities for a runtime to switch between workloads, particularly when multiple operations have been fused into a persistent megakernel.

This creates a scheduling challenge for LLM serving systems that must handle both interactive, latency-sensitive requests and background inference workloads.

The central motivation of this research is to investigate whether task-aware yielding within a megakernel can reduce scheduling delays while retaining the performance benefits of kernel fusion.

## Proposed Approach

The proposed mechanism introduces cooperative yielding into megakernel execution.

When an urgent workload arrives, the runtime requests the background megakernel to yield. The scheduler stops dispatching new background tasks, while active workers finish their current tasks and drain asynchronous operations.

Before exiting, the megakernel preserves its execution state in device memory, including:

- Task queue state.
- Dependency counters.
- Intermediate computation results.
- Graph execution progress.

Once the GPU becomes available, the runtime can relaunch the megakernel and resume execution from its saved state rather than restarting the entire workload.

## Research Challenges

This project focuses on three primary research questions:

1. **Safe stopping points:** How can a megakernel yield without losing completed work, duplicating tasks, or violating task dependencies?
2. **Yield and resume overhead:** What is the performance cost of saving execution state, releasing GPU resources, and relaunching the megakernel?
3. **Latency-aware scheduling:** Can selecting yielding points based on latency requirements provide better performance than using fixed execution boundaries?

## Evaluation

The proposed approach will be extended from the MPK runtime and evaluated on an NVIDIA A100 GPU, initially using Qwen3-1.7B and subsequently validating on Qwen3-8B.

The evaluation will consider workloads with varying request arrival patterns, context lengths, and batch sizes.

Key performance metrics include:

- **P99 first-token latency:** Measures responsiveness when a request arrives.
- **P99 inter-token latency:** Measures consistency during token generation.
- **Background throughput:** Measures tokens generated by background workloads.
- **Yield-response time:** Measures how quickly the megakernel releases GPU resources after a yield request.
- **Goodput:** Measures the number of requests per second that meet their latency targets.

The proposed mechanism will be compared against existing approaches, including MPK, vLLM with CUDA Graphs, CUDA priority streams, fixed execution quanta, and operator- or layer-level yielding.

## Expected Contribution

The expected outcome is a cooperative revocation mechanism for megakernels that enables GPU workloads to yield and resume while preserving task-graph execution state.

The research aims to characterize the trade-off between scheduling responsiveness and background throughput, and determine when task-aware yielding can improve predictable LLM serving under competing workloads.

## Repository layout

| path | what |
|---|---|
| `include/`, `src/`, `tests/` | Toy persistent megakernel: cooperative scheduler, ring-buffer queue and watchdog (A1), yield/resume (A2), per-task log (B1) |
| `tools/` | Independent correctness checker and tests (B1) |
| `mpk/` | Our MPK changes as patches against upstream: A3 yield/resume, task-boundary yield, A100 fixes. `mpk/setup_mpk.sh` builds the patched tree |
| `profiling/` | C2 MPK profiling report, A3 yield/resume tests and results on A100 |
| `workload/` | C3 workload generator (urgent and background classes; Poisson, bursty, trace arrivals) |
| `scripts/` | SLURM test scripts |

## How to test (Unity, A100)

```bash
mkdir -p logs
sbatch scripts/test_a100.sbatch              # toy megakernel with yield/resume + B1 checker
mpk/setup_mpk.sh                             # patched MPK at ~/mirage-a3
sbatch profiling/a3_yield_test.sbatch        # MPK yield/resume, bit-exact output check
python workload/test_gen.py                  # workload generator tests (CPU)
```
